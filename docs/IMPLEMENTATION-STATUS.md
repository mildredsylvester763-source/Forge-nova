# Implementation status

This document separates source code that exists from planned capabilities that have not yet been implemented.

## Implemented in source (initial foundation)
- NestJS/TypeScript backend bootstrap, environment validation, API version prefix, Helmet headers, request correlation IDs, and throttling.
- PostgreSQL/Prisma schema and a version-controlled initial SQL migration.
- Liveness and readiness endpoints.
- Account registration/login, bcrypt password hashing, opaque hashed refresh tokens, refresh rotation, revocation, and session-bound access-token validation.
- Organizations, memberships, workspaces, projects, and applications with membership-based access checks.
- Persistent project conversations and user messages, separated from application lifecycle.
- Text source file storage with immutable revision history, restore, optimistic concurrency, safe path validation, and high-confidence secret scanning.
- Application checkpoints that snapshot app metadata and source revision references, then restore atomically while preserving history and soft-deleting post-checkpoint files.
- Asynchronous AI source generation with structured-output validation, provider routing, non-executing TypeScript/JavaScript/JSON syntax checks, one metered repair attempt, atomic multi-file writes, conflict detection, secret/path checks, and honest NOT_RUN build-verification status.
- Work graph and node/dependency persistence, cycle validation, ready-node analysis, and recoverable AI planning leases.
- Provider-neutral adapters for OpenAI, Anthropic, Google AI, and Mistral; configurable routing/fallback; provider response normalization; and raw token/call usage metering.
- Internal durable job queue with atomic PostgreSQL claiming, worker leases, heartbeats, retry handling, cooperative cancellation, completion/failure recording, and authenticated job-status/cancel routes.
- Background worker loop with a concrete asynchronous work-graph planning handler and graceful shutdown cancellation.
- Raw resource usage event ledger; commercial prices and credit values are intentionally absent.
- Unit tests for health behavior, environment validation, path safety, secret scanning, AI routing, and plan parsing.
- Application verification subsystem: real non-executing static analysis (TypeScript parser diagnostics + JSON validation), real secret scanning over all live application files, and a structural package.json dependency audit. Each run persists a VerificationRun row with honest status (PASSED / FAILED / SKIPPED), severity counts, capped findings, and evidence (engine version, analyzed file counts, unsupported files). Zero analyzable files is recorded as SKIPPED, never a fabricated PASS. Verification is exposed via authenticated project-role endpoints (POST run, GET list, GET inspect) and via a SECURITY_SCAN job handler on the durable queue; BUILD and TEST kinds exist in the enum but deliberately cannot be requested because no real build/test execution exists yet.
- Reference ingestion (text references): ReferenceDocument storage (SPEC/TRANSCRIPT/NOTES/OTHER kinds) with strict input validation (title 200 chars, content 50,000 chars, named refusals), AI-backed structured requirement extraction (1-30 requirements with MUST/SHOULD/COULD priorities, up to 20 open questions) via the provider router, strict extraction parsing with named refusals, honest EXTRACTION_FAILED status with recorded errors, authenticated CRUD + extract endpoints, and a RESEARCH job handler. Image, Figma, video, and URL references are deliberately refused by name because no binary ingestion infrastructure exists yet.
- GitHub Actions workflow for schema validation, type-checking, unit tests, and backend build. This is source-code CI only; it does not deploy.
- Functional product-flow test suite (src/functional/product-flows.spec.ts): 31 end-to-end flows that boot the real NestJS app against the real CI PostgreSQL database and exercise the actual product path over HTTP - register, login, refresh rotation with replay rejection, /me, auto-created organization and workspace, project creation, application creation, conversations with messages, source-file writes with optimistic-concurrency conflicts, secret-in-file refusal, verification runs (PASSED with evidence, FAILED dependency audit, SKIPPED for empty apps), verification history, reference creation with IMAGE/secret refusals, honest EXTRACTION_FAILED extraction, tenant isolation between users, and logout revocation. The suite skips cleanly when no database or JWT secret is configured. A deployment-readiness subsystem (src/deployments/) assesses whether an application is honestly deployable before any deployment record is created: entrypoint detection (index.html, src/index.ts, main.py, or a package.json start script), manifest validation, a verification gate (the latest recorded run per kind must not be FAILED), and a secret-material gate. Deployment intents that pass readiness are recorded with an explicit adapter: none-configured marker and an execution note stating that no deployment adapter exists in this environment - GENESIS records intent and readiness evidence, it never claims execution. BLOCKED applications are refused with the full readiness report. DEPLOYMENT remains a deliberately handler-less JobType: no infrastructure adapter exists yet, and pretending otherwise would be dishonest. 10 readiness-engine unit cases and 3 functional deployment flows extend the suite. This suite caught and led to the fix of a real boot bug: JwtModule was module-scoped, so any feature module using JwtAuthGuard (Generation, Applications, and others) failed dependency resolution when the full AppModule was actually instantiated; JwtModule is now registered globally.
- Membership lifecycle and organization governance: role changes, member removal, and atomic ownership transfer (target becomes OWNER, actor becomes ADMIN in one transaction, never two owners) with a membership-policy engine (named refusals for owner assignment outside the dedicated transfer workflow, last-owner protection, unknown-membership 404s), admin-only organization audit-trail listing, application update/archive/restore and project restore with archived-state guards, and race-safe member removal (two admins pressing remove simultaneously get exactly one 200 and one clean 404, with a single audit row).
- Concurrency and double-tap scenario suite (src/functional/concurrency-scenarios.spec.ts): 7 scenario tests that boot the real app against the real CI PostgreSQL and hammer actual functions with simultaneous requests: duplicate registration double-tap (exactly one 201, one 409), refresh-token replay race (exactly one rotation; the stolen token dies), two admins racing to add the same member (one 201, one 409, exactly one membership row), two admins racing role changes on the same member (no server errors, consistent final state), two admins pressing member removal at the same time (exactly one 200, one audit row), ownership-transfer double-tap (never two owners), three writers racing the same file revision (exactly one 201, clean 409s), same-path create double-tap, archive double-tap idempotency with exactly-once restore, and write blocking while archived. This suite exposed and led to the fix of two real concurrency defects: an unguarded membership delete racing into a raw Prisma P2025 (500), and serializable file-write conflicts (Prisma P2034) surfacing as 500 instead of a retryable 409.
- Operation race suite (src/functional/operation-races.spec.ts): 15 scenario tests that hammer the durable job queue, checkpoints, verification runs, and work-graph planning leases with simultaneous requests and double-taps - over the real HTTP surface plus the exact worker service calls a production worker makes (claim, heartbeat, complete, fail, acknowledge-cancellation) against the real CI PostgreSQL: plan double-tap queues exactly one job row via the planning idempotency key; cancel replay is an honest no-op and replanning requeues the same job instead of duplicating it; two admins pressing cancel at the same time produce exactly one state transition plus uniform VIEWER/unknown/foreign 404s; cancel-versus-completion races end exactly one way (completion wins, or the worker acknowledges cancellation - never a 500); zombie workers on expired leases are refused after another worker takes over; two workers racing a FIFO claim get exactly one winner; cancel-versus-claim on an expired lease stays consistent; a double-tapped checkpoint restore applies exactly one content change; restore replay is an idempotent no-op; restore-versus-write races resolve as [201, 409] with a contiguous immutable revision chain; simultaneous checkpoint snapshots stay consistent; double-tapped verification runs execute independently; planning-lease races grant exactly one lease (one 409 Conflict, one 503 unavailable) and always return the graph to a recoverable DRAFT; live leases are refused and expired leases recovered. The suite exposed and led to the fix of a real restore-idempotency defect: restore() skipped files by revision number instead of content state, so a double-tapped restore re-wrote identical content as a pointless duplicate revision; restore now compares content hash, deletion, and language state and is genuinely idempotent. Claim-race determinism in the shared CI queue is guaranteed by backdating the suite's own jobs so they are the oldest claimable rows in the FIFO. Grounded in market research: Stripe idempotency semantics and GitHub Actions cancellation semantics (202/409, exactly one winner). This suite exposed and led to the fix of a third real race defect: enqueue() only recovered from a lost unique-key insert race when the payloads matched byte for byte, so two different write members pressing plan at the same moment could surface a raw 409 (the requestedBy metadata differs between them) or an unhandled Prisma P2034 write conflict (500); enqueue() now recovers from both P2002 and P2034 insert races with a bounded re-read of the raced row, and the plan route converges the loser on the winning job, so both members receive the same clean 201 with the same job id.
- Data race suite (src/functional/data-races.spec.ts): 15 scenario tests that hammer the remaining pushed surfaces - deployment intents, reference documents, conversations, and file delete/restore - with simultaneous requests and double-taps over the real HTTP surface against the real CI PostgreSQL: two admins pressing deployment create at the same time produce two independent honest intents (each with the none-configured adapter and the execution disclaimer) while read-only members, unknown applications, and unknown deployments get uniform 404s; blocked-deployment double-taps are refused identically (400 with the readiness report, zero rows recorded); a file delete double-tap produces one tombstone and a clean 404; delete-vs-write and restore-vs-delete races resolve with exactly one winner ([200, 409] or [201, 409]) and a contiguous immutable revision chain; a double-tapped revision restore applies exactly once; a deleted file is honestly resurrected through an expectedRevision write; a reference delete double-tap yields exactly one 200 and one clean 404 with a single audit row; a deletion racing an extraction never 500s (the loser gets 502/503 or 404 honestly); double-tapped extractions run as independent honest attempts; simultaneous conversation messages from two members both persist while read-only members can read but never post; an archive racing a message ends 200 with the message either stored or cleanly refused (409) and posts blocked afterwards; conversation creation double-taps produce independent honest records. This suite exposed and led to the fix of three real race defects: FileService.restore()/delete() did not translate serializable write conflicts (Prisma P2034) into a retryable 409 the way write() does, so a restore or delete racing another write on the same file could surface a raw 500; ReferencesService.remove() could throw a raw Prisma P2025 (500) when two members deleted the same reference simultaneously (now a guarded deleteMany - exactly one winner); and ReferencesService.extract() could throw raw Prisma P2025 (500) when a reference was deleted mid-extraction in either the success or the failure path (now an honest 404).
- GENESIS API key system: organization-scoped keys with SHA-256-only storage (the plaintext is returned exactly once at creation and never persisted), the gn_live_ environment-prefixed format, masked display hints for dashboard identification, granular per-resource scopes (READ_ORGANIZATION, READ_PROJECTS, READ_APPLICATIONS - a scope may only exist when a key-authenticated endpoint actually honors it), optional expiry with past-date refusal, instant guarded revocation (two simultaneous revocations produce exactly one success and one clean 404, with a single audit row), last-used tracking, per-key fixed-window rate limiting (instance-local and honestly documented as not distributed), and a uniform 401 that never discloses whether a key was unknown, revoked, or expired. Key management routes (create/list/revoke) are JWT- and admin-gated with full audit events; the key-authenticated read surface (genapi me/projects/applications) is tenant-bounded to the key is own organization. The design combines Stripe is environment-prefixed restricted keys with GitHub fine-grained PAT scope and expiry semantics. 10 engine unit cases (key derivation vectors, hint masking, prefix strictness, scope and expiry laws, a 500-key uniqueness sweep) and 13 functional flows (reveal-once, masked listing, scope enforcement per endpoint, uniform 401s, expiry laws, outsider 404s, revoke double-tap race, per-key 429 enforcement, audit trail).
- GENESIS API key write surface: a new WRITE_APPLICATIONS scope, granted at key creation and honored exclusively by six real key-authenticated write endpoints under /genapi (file write with optimistic concurrency, checkpoint create, checkpoint restore, verification run, application archive, application restore) - a scope may only exist where a real endpoint honors it. The key IS the authorization: every write is tenant-bounded through the data path application to project to workspace to organization equal to the key organization, with foreign, missing, and archived targets all refused by the same uniform 404 that never reveals whether the application exists. Writes are attributed honestly: file rows carry the creating user id from the key creator (never a fake system user; a key whose creator was deleted attributes to null), verification runs record their triggering user, and audit rows are stamped via genapi with the acting key id and name so key actions appear in the organization audit trail next to human ones. Revocation and expiry stop writes instantly with the same uniform 401 as the read surface, and a read-scoped key is refused 403 with zero side effects. The design mirrors GitHub fine-grained PAT write permissions: explicit per-resource scopes, every write attributable to a specific key and creator. 7 new engine policy unit cases (actor derivation, attribution, audit stamping, audit organization scoping, single-source-of-truth scope checks, plus a 500-case randomized actor and scope sweep) and a 14-test functional suite against the real app and real PostgreSQL: honest attribution of a keyed file write, read-key refusal with zero rows, optimistic-concurrency 201/409s, a same-key double-tap update race and a two-key race each ending in exactly one 201 and one 409 with a contiguous immutable revision chain, cross-tenant uniform 404s with zero trace across all four write kinds, checkpoint snapshot/drift/restore with idempotent replay, verification array runs with triggeredBy attribution and reader refusal, archive/restore double-taps including write-blocked-while-archived, revoked-key instant refusal with no rows, expiry enforcement on a live key, uniform 401s, and audit-honesty assertions against the real audit rows.
- GENESIS API key read surface: five new key-authenticated read endpoints under /genapi (file list, file read, checkpoint list, verification list, verification inspect) honoring the existing READ_APPLICATIONS scope - no new scope was invented, because that scope already names exactly these reads. Every read is tenant-bounded with the same uniform 404 that never reveals whether an application exists; list and inspect shapes mirror the JWT surface (file lists omit content by design, single-file reads include it); deleted files stay hidden from keyed reads; foreign runs are invisible exactly like unknown ones; and reads remain available on archived applications because archive blocks writes, not reads - the same law the JWT surface follows. There is deliberately no audit row for reads. A 14-test functional suite against the real app and real PostgreSQL covers shape parity with the JWT surface, single-file read content, deleted-file invisibility, write-only-key 403 with zero side effects, cross-tenant uniform 404s with a single identical refusal message, unknown-application 404s, checkpoint attribution, verification history parity, run inspection with the persisted findings shape, unknown and foreign run 404s, reads-on-archived plus write-blocked-while-archived, revoked-key instant refusal, expiry enforcement, and uniform 401s across every read endpoint.
- GENESIS API key async-work surface: four key-authenticated read endpoints under /genapi (work-graph list, work-graph inspect, work-graph validation, queued-job inspection) honoring the existing READ_APPLICATIONS scope, plus one audited write endpoint (job cancel) honoring WRITE_APPLICATIONS - grounded in GitHub Actions REST semantics, where reading a workflow run needs only the actions-read permission while canceling a run needs write, and only queued or in-progress runs are cancellable (canceling an already-finished job is an honest no-op that returns the current status without a new audit row, exactly like replaying a cancel). Every read and cancel is tenant-bounded through the application-to-organization check with the same uniform 404 that never reveals whether the application, graph, or job exists; reads stay possible on archived applications because archive blocks writes, not reads, while cancel is blocked on archived applications with the same 404 as for unknown ones. Cancellation is attributable and exactly-once: the audit row is written only when a job actually transitions to CANCELLED (never on replays or lost races), stamped via genapi with the acting key id, and two keys racing the same cancel produce exactly one transition and one audit row attributed to a single key. The job-queue service gained a shared job view select and a cancelForKey path that reuses the same applyCancellation core the worker-facing route uses, so JWT and key cancellations can never drift apart. A 16-test functional suite against the real app and real PostgreSQL covers graph list/inspect/validate and job inspect parity with the JWT surface (including honest dependency shapes), cross-application and foreign uniform 404s with a single identical refusal message, write-only-key 403s on every read, read-key cancel refusal with zero side effects, keyed cancel with full audit attribution, replay as a no-op without a second audit row, a two-key cancel race ending in exactly one transition and one audit row, reads-on-archived plus cancel-blocked-while-archived, revoked-key instant refusal, expiry enforcement, and uniform 401s across every endpoint.
- Integration and connector platform: a 7-connector catalog (github, gitlab, vercel, netlify, figma, notion, custom) with per-connector credential contracts, admin-gated connection lifecycle (create/list/test/delete) where credentials are stored raw server-side but only field names and value lengths ever leave the vault, honest REAL outbound connection testing (3s budget, succeeded / failed / unreachable outcomes with the actual error detail recorded), and webhook endpoints with reveal-once whsec_ signing secrets (returned exactly once at creation, never listed again), Stripe-style signed payloads (t=<unix>,v1=<hex> HMAC-SHA256 over timestamp.body, 300s tolerance, constant-time comparison), an event subscription grammar (8 known events, entity wildcards, all), dispatch that creates one delivery row per matching endpoint plus a synchronous signed POST, an exponential retry backoff (60s / 300s / 1800s / 7200s / 28800s, 5 attempts, then EXHAUSTED - never forever), and a manual retry route whose attempt claim is an atomic updateMany that flips PENDING to IN_FLIGHT, so two simultaneous retries produce exactly one 201 and one 409 and never a double send, whatever order the racers read the row in. Grounded in market research: Stripe webhook signatures, GitHub HMAC constant-time comparison, and Slack Events API retry semantics. 12 engine unit cases (signature determinism, refusals, and tolerance edges; subscription grammar and matching; backoff schedule and refusals; catalog and credential no-leak guarantees; plus 500-case seeded sweeps per engine) and 15 functional flows against a real local node:http receiver: catalog and uniform 404s, no credential echo, malformed refusals, connection create/delete double-taps, real outbound test outcomes (CONNECTED / failed HTTP 500 / unreachable), reveal-once secrets, end-to-end signed delivery verified with the very signature engine that produced it plus a tamper case, honest zero-match dispatches, backoff and exhaustion laws, recovery, retry double-tap with exactly one receiver hit, endpoint delete cascade, and the full audit trail.
- Automatic lifecycle event emission: GENESIS now fires system events for every API-caused state change - application.created/updated/archived (update and restore both emit application.updated), checkpoint.created/restored, deployment.recorded, verification.completed, and reference.created. A contracts engine (src/integrations/engine/system-events.engine.ts) is the single source of truth: each event guarantees an exact field set, every field is validated by name (system-event-unknown, payload-not-an-object, field-missing, field-invalid refusals), and the emitted payload carries exactly the contract fields - never padded, never partial. Emission follows the outbox law the market leaders practice (Stripe fires an event for every API-caused state change and a webhook failure never fails the parent API call): it runs AFTER the parent operation and its audit row commit, is best-effort, and can NEVER throw or roll back the parent flow; delivery failures are recorded on the delivery row where the retry route can reach them, and there is deliberately no audit row for emission itself (the parent action row is the audit, the delivery rows are the evidence). Emission is silent for refused operations (validation refusals, readiness-blocked deployments, role refusals, unknown resources). 8 engine unit cases (per-contract acceptance, named refusals for every failure mode, null-versus-malformed field semantics, contract-only field drops, and a 500-case mulberry32 seed-42 sweep cross-checked against an independent validator) plus 13 functional flows against a real local node:http receiver: signed application.created delivery verified with the very signature engine that produced it plus a tamper case, the full update/archive/restore event lifecycle, checkpoint events with honest changedFiles counts, reference and verification events with exact run identities, silence on a readiness-blocked deployment (400 with the readiness report and zero emissions), a real deployment.recorded event after an honest readiness pass, the never-fails-parent law proven with a dead endpoint (parent still 201; the dead endpoint keeps a PENDING delivery with the recorded error), a two-writer create race emitting exactly one event per application with valid signatures, zero emissions for refused operations, per-endpoint subscription honesty (a checkpoint-only endpoint receives checkpoint events and nothing else), and an honest audit trail (organization-scoped rows only in the org listing; parent-action rows verified directly; zero emission ghost rows).
